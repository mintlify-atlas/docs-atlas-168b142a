Certain types and traits in the standard library receive special treatment from the Rust compiler itself. This page documents those special features — behavior that cannot be replicated with user-defined types — including the heap allocation types, interior mutability, marker traits, auto traits, and the `Drop` trait.

---

## `Box<T>`

`Box<T>` is the primary heap allocation type in Rust. It has several compiler-special features not available to user-defined types:

- **Dereferenceable place**: The dereference operator `*` on a `Box<T>` produces a place that can be moved from. This means the `*` operator and the destructor of `Box<T>` are built into the language.
- **Receiver type**: Methods can take `Box<Self>` as a receiver.
- **Orphan rule exception**: A trait may be implemented for `Box<T>` in the same crate as `T`. This exception to the orphan rules is not available for other generic types.

```rust
let boxed: Box<i32> = Box::new(42);
let val: i32 = *boxed; // dereference and move out of Box
```

`Box<T>` is also special with respect to closure captures: the compiler can precisely capture fields *through* a `Box<T>` dereference (unlike other `Deref` implementations):

```rust
struct S(String);
let b = Box::new(S(String::new()));
let c_box = || {
    let x = &(*b).0; // captures (*b).0 by ImmBorrow, not all of b
};
```

## `Rc<T>` and `Arc<T>`

Both `Rc<T>` (single-threaded reference counted) and `Arc<T>` (atomically reference counted) have one compiler-special feature:

- **Receiver type**: Methods can take `Rc<Self>` or `Arc<Self>` as a receiver.

This enables method calls on values wrapped in reference-counted pointers without going through `Deref` explicitly.

## `UnsafeCell<T>` — Interior Mutability Root

`std::cell::UnsafeCell<T>` is the only allowed way to disable the compiler's rule that the value pointed to by a shared reference cannot be mutated. It is the foundational primitive for *interior mutability* in Rust.

When `UnsafeCell<T>` is immutably aliased, it is still safe to mutate or obtain a mutable reference to the `T` it contains (though doing so requires `unsafe` code). All standard library interior mutability types (`Cell<T>`, `RefCell<T>`, `Mutex<T>`, `RwLock<T>`, atomic types) are built on top of `UnsafeCell<T>`.

```rust
use std::cell::UnsafeCell;

struct MyCell<T> {
    value: UnsafeCell<T>,
}

impl<T: Copy> MyCell<T> {
    fn new(val: T) -> Self {
        MyCell { value: UnsafeCell::new(val) }
    }

    fn get(&self) -> T {
        unsafe { *self.value.get() }
    }

    fn set(&self, val: T) {
        unsafe { *self.value.get() = val; }
    }
}
```

<Warning>
It is undefined behavior to have multiple `&mut UnsafeCell<T>` aliases. `UnsafeCell<T>` only permits shared mutation, not multiple mutable aliases.
</Warning>

`UnsafeCell<T>` also ensures that `static` items with interior mutability are not placed in read-only memory.

`UnsafeCell<T>` is **invariant** over `T`, which prevents unsound lifetime shortening through shared references to mutable state.

## `PhantomData<T>`

`std::marker::PhantomData<T>` is a zero-sized, 1-aligned type that tells the compiler to treat the enclosing type as if it owns a `T`, for the purposes of:

- **Variance**: `PhantomData<T>` is covariant over `T`, affecting the variance of the struct containing it.
- **Drop check**: The compiler uses `PhantomData<T>` to determine that the type logically owns a `T` and may drop it.
- **Auto traits**: The struct will implement auto traits (`Send`, `Sync`, etc.) only if `T` does.

Common use cases for `PhantomData<T>`:

```rust
use std::marker::PhantomData;

// A raw pointer wrapper that is covariant over T and logically owns a T
struct MyVec<T> {
    ptr: *mut T,
    len: usize,
    cap: usize,
    _marker: PhantomData<T>,  // tells the compiler we own T values
}

// A type that is invariant over 'a (holds a mutable reference-like thing)
struct Invariant<'a> {
    _marker: PhantomData<&'a mut ()>,
}
```

## Auto Traits

Auto traits are traits whose implementations are automatically generated by the compiler based on the types of a type's fields. The auto traits in Rust are: `Send`, `Sync`, `Unpin`, `UnwindSafe`, and `RefUnwindSafe`.

The automatic implementation rules are:

- `&T`, `&mut T`, `*const T`, `*mut T`, `[T; n]`, and `[T]` implement the trait if `T` does.
- Function item types and function pointers automatically implement all auto traits.
- Structs, enums, unions, and tuples implement the trait if all of their fields do.
- Closures implement the trait if all of their captured values do.

### `Send`

`Send` indicates that a value of this type is safe to send from one thread to another (i.e., ownership can be transferred across thread boundaries):

```rust
use std::thread;

let s = String::from("hello");
thread::spawn(move || {
    println!("{}", s); // s: String is Send, so this is allowed
});
```

### `Sync`

`Sync` indicates that a value of this type is safe to share between multiple threads via a shared reference (`&T` is `Send` if `T: Sync`):

```rust
use std::sync::Arc;
use std::thread;

let shared = Arc::new(42i32); // i32: Sync, so Arc<i32>: Send
let shared2 = Arc::clone(&shared);
thread::spawn(move || {
    println!("{}", *shared2);
});
```

`Sync` must be implemented for all types used in immutable `static` items.

### Negative Implementations

Auto traits can have *negative implementations* that override the automatic ones. For example, `*mut T` has a negative implementation of `Send`, so raw mutable pointers are never `Send` even if `T: Send`. There is no stable way for user code to add negative implementations.

Auto traits may be added as additional bounds to any trait object: `Box<dyn Debug + Send + UnwindSafe>` is valid.

## Marker Traits

### `Copy`

`Copy` changes the semantics of a type: values of `Copy` types are bitwise-copied on assignment rather than moved.

`Copy` can only be implemented for types that:
- Do not implement `Drop`.
- Have all fields that are themselves `Copy`.

`Copy` is automatically implemented by the compiler for:
- Tuples of `Copy` types.
- Function pointers.
- Function item types.
- Closures that capture only `Copy` types (or no values at all).

```rust
let x: i32 = 42;
let y = x;       // x is Copy, so it is copied
println!("{}", x); // x is still valid
```

### `Sized`

`Sized` indicates that the size of a type is known at compile time. It is always implemented automatically by the compiler — you can never implement `Sized` manually. Type parameters have an implicit `Sized` bound by default; this is relaxed with `?Sized`.

```rust
fn print_size<T: Sized>() {
    println!("{}", std::mem::size_of::<T>());
}

// Allow DSTs by relaxing the Sized bound
fn process<T: ?Sized>(value: &T) {
    // ...
}
```

## `Deref` and `DerefMut`

`Deref` and `DerefMut` overload the unary `*` operator and participate in method resolution and deref coercions. When you call a method on a type, Rust automatically follows chains of `Deref` implementations to find the method.

Common deref chains:
- `String` → `str` (via `Deref<Target = str>`)
- `Vec<T>` → `[T]` (via `Deref<Target = [T]>`)
- `Box<T>` → `T` (via `Deref<Target = T>`)

```rust
let s = String::from("hello");
let len = s.len(); // String derefs to str, which has .len()
```

## `Drop` Trait and Drop Order

The `Drop` trait provides a destructor that runs when a value is destroyed (when it goes out of scope, is assigned over, or is explicitly dropped). Only one of `Drop` and `Copy` may be implemented for a given type.

```rust
struct PrintOnDrop(&'static str);

impl Drop for PrintOnDrop {
    fn drop(&mut self) {
        println!("{}", self.0);
    }
}

{
    let _a = PrintOnDrop("A");
    let _b = PrintOnDrop("B");
} // prints "B" then "A" — reverse declaration order
```

### Drop Order Rules

Variables are dropped in reverse order of declaration. The destructor of a type runs as follows:

1. If `T: Drop`, call `<T as Drop>::drop`.
2. Recursively run the destructor of all fields:
   - Struct fields: dropped in **declaration order**.
   - Enum fields: dropped in declaration order for the active variant.
   - Tuple fields: dropped in order.
   - Array/slice elements: dropped from first to last.
   - Closure captures by move: dropped in unspecified order.

```rust
# struct PrintOnDrop(&'static str);
# impl Drop for PrintOnDrop {
#     fn drop(&mut self) {
#         println!("{}", self.0);
#     }
# }
let tuple = (PrintOnDrop("Tuple first"), PrintOnDrop("Tuple second"));
// When tuple drops: "Tuple first" then "Tuple second"
```

<Note>
You can suppress the destructor using `std::mem::forget` or `std::mem::ManuallyDrop`. This is safe even for non-`'static` types. Types must not rely on their destructor always being called for soundness.
</Note>

## Dynamically Sized Types and the `Sized` Bound

Dynamically sized types (DSTs) have sizes known only at runtime. The DSTs in Rust are `[T]`, `str`, `dyn Trait`, and structs with a DST last field.

DSTs can only be used:

- Behind pointer types (`&T`, `&mut T`, `*const T`, `*mut T`, `Box<T>`).
- As type arguments with a `?Sized` bound.
- In trait definitions where `Self: ?Sized` (the default).
- As the last field of a struct.

Pointers to DSTs are *fat pointers* that include metadata alongside the data pointer:
- Slices (`[T]`, `str`): carry the number of elements or byte length.
- Trait objects (`dyn Trait`): carry a pointer to the vtable.

```rust
// A struct whose last field is a DST — the struct itself is a DST
struct Header {
    version: u32,
    data: [u8],  // DST tail
}
```

<Note>
Variables, function parameters, `const` items, and `static` items must be `Sized`. You cannot store a bare DST on the stack.
</Note>
